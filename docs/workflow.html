MSA workflow

Pipeline for (a) auto-generating a WebPPL world-model from a natural-language scenario (the "MSA" method of Wong et al. 2025), (b) running posterior inference on the resulting program, and (c) comparing its samples against a gold reference.

Stage 1: scenarios

Each scenarios/{name}.txt is annotated with marker tags around five regions (scenario, language-to-code parse, scratchpad / concept trace, WebPPL model). convert_scenarios.py reads these and emits scenarios/{name}.json with eight fields stored as lists of lines: background, conditions, query, parsed_conditions, parsed_queries, informal, graph, model. These JSONs are the ground-truth examples that the formalize pipeline consults as in-context demos.

Stage 2: formalize (LLM → WebPPL)

formalize.py implements the 3-step pipeline from the paper. For a target scenario, it uses the other four scenarios as shuffled in-context examples and calls an LLM through OpenRouter via litellm:

  1. Parse (generate-parsing.txt, T=0.2): translate natural-language conditions and queries into WebPPL function calls wrapped in <START_LANGUAGE_TO_WEBPPL_CODE> markers.
  2. Graph (generate-graph.txt, T=0.5): generate k_graph candidate <START_SCRATCHPAD> blocks (informal background + concept-dependency trace) in parallel using a ThreadPoolExecutor. Each is scored 0–10 by an LLM call to score-graph.txt; the best wins. With k_graph>1 the K generate-and-score pairs all happen concurrently, so wall-clock time is roughly one round-trip rather than 2K.
  3. Model (generate-model.txt, T=0.2): produce the final <START_WEBPPL_MODEL> body, given the scenario, parse, and best graph.

LLM labels are short aliases — pro → openrouter/google/gemini-3.1-pro-preview, flash → openrouter/google/gemini-3-flash-preview, etc. Override via MSA_LLM_PRO=... env var, or pass the full model id directly (any litellm-supported provider).

Stage 3: top-level driver

msa.py --scenario {name} [--expt EXPT] [--llm pro] [--k-graph 8] glues everything together:

  1. Calls formalize() to produce the WebPPL source.
  2. Prepends var queryLabels = {...} (built from the scenario's Query N: lines) so the LLM-generated model — which doesn't know about queryLabels — works with the inference wrapper.
  3. Saves to models/{method}/{scenario}.wppl where method = msa_{llm}{suffix}: _e{N} for numeric expts (e.g. --expt 1 → msa_pro_e1) and _{name} for word expts (--expt smoke → msa_pro_smoke).
  4. Runs get_samples.js for inference, then compare_samples.py against the gold1 reference.

Stage 4: model contract

Each .wppl file under models/{method}/ defines:

  • model — a function with no arguments, returning a dict of query values. Calls condition(...) for observed evidence.
  • queryLabels — a dict mapping each query key to a human-readable description.

The model file does not run inference itself; that's the driver's job.

Stage 2: sampling

get_samples.wppl — the inference driver

Reads N and METHOD from process environment, runs Infer({model, method, samples: N}), and emits two blocks to stdout between marker lines:

__SAMPLES_BEGIN__
[ {query1: ..., query2: ...}, ... ]
__SAMPLES_END__
__QUERIES_BEGIN__
{ "query1": "...", ... }
__QUERIES_END__

get_samples.js — the Node wrapper

Concatenates the chosen model file with get_samples.wppl into a temp file (WebPPL's CLI accepts only one program file), invokes webppl with --random-seed, parses the marker blocks, and writes a JSON file of the form:

{
  "queries": {"query1": "Bob rank (out of 100)", ...},
  "samples": [{"query1": 62, "query2": 93, ...}, ...]
}

Invocation:

node get_samples.js --model {biathlon|canoe|diving|exam|tug} \
                    [--method LABEL]    (default: gold)              \
                    [--n N]             (default: 1000)              \
                    [--seed SEED]       (default: 0)                 \
                    [--algo ALGO]       (default: rejection)         \
                    [--model-dir DIR]   (default: models/{method})

The wrapper reads {model-dir}/{model}.wppl (default models/{method}/{model}.wppl), runs webppl with --random-seed {seed}, and writes samples/{method}/{model}.json. Experiment labels live in the method name (e.g. msa_pro_e1), not in the model file name. Examples:

  • --method gold --seed 0 → reads models/gold/tug.wppl, writes samples/gold/tug.json (reproduces the existing gold reference byte-for-byte).
  • --method gold1 --seed 1 --model-dir models/gold → reuses the gold source with a different seed, writes samples/gold1/tug.json.
  • --method msa_pro_e1 → reads models/msa_pro_e1/tug.wppl, writes samples/msa_pro_e1/tug.json.

Note: --method here is a label for the output directory (e.g. gold, gold1, learned), not the webppl inference algorithm — that's --algo (rejection / MCMC / SMC / ...).

Webppl quirks worth knowing

  • WebPPL's CLI takes one program file. Multiple files must be concatenated externally.
  • Inside .wppl, Node's require is not in scope — file I/O must happen in the host wrapper.
  • parseInt and Number silently abort the CPS-transformed program. Use JSON.parse or arithmetic coercion (e.g. s * 1) instead.
  • Methods supported by Infer: rejection (exact, slow for tight conditions), MCMC, SMC, etc.

Intermediates — debugging the formalize pipeline

For each formalize() invocation, every LLM call is logged to intermediates/{method}/{scenario}/:

FileContents
1_parse_prompt.txt Full prompt sent for step 1 (template + in-context examples + target scenario).
1_parse_response.txt Raw LLM response.
1_parse_block.txt Extracted <START_LANGUAGE_TO_WEBPPL_CODE>...<END_…> block, with markers, ready to feed into step 2.
2_graph_{k}.txt For each of k_graph candidates: extracted <START_SCRATCHPAD>...<END_…> block plus the raw scoring response. First line is # Score: <0-10>.
2_graph_{k}_response.txt Only present if extraction failed; holds the raw response for that sample so you can see why the markers were missing.
2_graph_best.txt The winning graph, with its index and score in a comment header.
3_model_prompt.txt Full prompt sent for step 3.
3_model_response.txt Raw LLM response.
3_model.wppl Extracted model body, markers stripped — what formalize() returns.

Smoke test

test/msa_smoke.py runs the full pipeline on tug with --llm flash --k-graph 1 --expt smoke, which is ~3 LLM calls total and finishes in seconds. Use it as a fast end-to-end check whenever you change the prompts, the wrapper logic, or the comparison code; outputs land at models/msa_flash_smoke/, samples/msa_flash_smoke/, and comparisons/gold1_vs_msa_flash_smoke/tug/.

Stage 3: comparison

compare_samples.py

python compare_samples.py --model {model}      \
                          --method1 {m1}       \
                          --method2 {m2}       \
                          [--bins 30]

Reads samples/{m1}/{model}.json and samples/{m2}/{model}.json, then for each query writes a 2×1 panel histogram and computes:

  • Jensen–Shannon distance — bin-based, in [0,1] bits. 0 = identical histograms; 1 = disjoint supports.
  • Wasserstein (Earth-Mover) distance — on raw samples, in the unit of the query.

Outputs are written to comparisons/{m1}_vs_{m2}/{model}/:

  • query{q}.png — one per query, top panel = m1, bottom panel = m2, shared axes.
  • jsd.png — bar chart of JS distance per query.
  • comparison.html — index page embedding all figures.

Stage 4: interpreting JS distance

The JS distance between two empirical histograms drawn from the same distribution has a non-zero expectation that depends only on the number of bins K and the sample size N:

E[JS dist] ≈ √(K−1.5) / (4 N ln 2)

For N=1000, K=30 (our default) this evaluates to ~0.10, which is exactly the floor observed when comparing two independent gold-vs-gold runs (gold vs gold1). See docs/jsd.tex for the derivation.

The implication: JS distance < ~0.10 is consistent with the same distribution at these settings, and is not itself evidence of agreement or disagreement. Use it as a relative magnitude across queries, not as an absolute test.

Recommended P-vs-Q test

If the goal is to decide whether two methods produce samples from the same posterior (per query), a few options are stronger than thresholding JS distance:

TestWhat it doesWhen to use
Two-sample Kolmogorov–Smirnov (scipy.stats.ks_2samp) Largest gap between empirical CDFs of the raw samples. No binning. Returns a p-value automatically calibrated for N. Default per-query test. Cheap, parameter-free.
Permutation test on Wasserstein distance Compute observed Wasserstein on raw samples; pool the two samples and randomly relabel many times to build a null distribution; report p-value. When you want a metric whose magnitude is interpretable (in the unit of the query) plus calibrated p-value.
Anderson–Darling 2-sample (scipy.stats.anderson_ksamp) Like KS but weights tails more. When tail behaviour matters (e.g. rare-event queries).
MMD with Gaussian kernel + permutation Kernel two-sample test; multivariate-friendly. If you want to test joint agreement across queries, not just marginal.

On the gold-vs-gold yardstick

The current experiment (gold vs gold1) is a useful sanity check: it measures the noise floor under the null. But because any reasonable test should fail to reject in this case, the magnitude of the gold-vs-gold gap mostly tells you about your test's variance, not its discriminative power. A more informative yardstick is to:

  1. Estimate the null distribution of your chosen test statistic by splitting one large gold run into halves repeatedly (or running with many seeds) — this gives a calibrated cutoff at any desired false-positive rate.
  2. Apply the same statistic to gold vs whatever alternative method you actually care about. Compare to the null cutoff.

If you only need one number, ks_2samp per query plus a Bonferroni-corrected family p-value is probably the cleanest move.
