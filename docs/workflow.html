MSA workflow

Pipeline for (a) auto-generating a WebPPL world-model from a natural-language scenario (the “MSA” method of Wong et al. 2025), (b) running posterior inference on the resulting program, and (c) comparing its samples to a hand-crafted gold model run on the same test scenario.

Stage 1 — train and test scenarios

Each data/train-scenarios/{sport}.txt is annotated with marker tags around five regions and converted to JSON via convert_scenarios.py. The resulting {sport}.json has fields background, conditions, query, parsed_conditions, parsed_queries, informal, graph, model (each as a list of lines so the JSON renders readably). These are the in-context demos.

Each data/test-scenarios/e{1,2}/scenarios/{id}.txt is a plain BACKGROUND / CONDITIONS / QUERIES vignette (no annotations — that's what we're testing the LLM on). The 7 vignettes per sport covered by human data are listed in data/test_ids.json; the full test directory holds 15 per sport.

Naming convention (sports): biathalon, canoe-race, tug-of-war (typo and hyphenation matching the Wong et al. dataset). Diving and exam exist only as train scenarios.

Stage 2 — formalize (LLM → WebPPL)

formalize.formalize(target, exclude_sport, llm, ...) implements the 3-step pipeline:

  1. Parse (generate-parsing.txt, T=0.2): translate NL conditions/queries into WebPPL stubs, wrapped in <START_LANGUAGE_TO_WEBPPL_CODE> markers.
  2. Graph (generate-graph.txt, T=0.5): generate K candidate <START_SCRATCHPAD> blocks in parallel (one ThreadPoolExecutor per K, releasing the GIL during LLM I/O). Each is scored 0–10 by an LLM call to score-graph.txt; the best wins.
  3. Model (generate-model.txt, T=0.2): produce the <START_WEBPPL_MODEL> body given scenario + parse + best graph.

In-context demos: the four train scenarios that don't match the test sport. So testing a biathalon vignette uses canoe-race + tug-of-war + diving + exam as examples.

LLM access via litellm against OpenRouter. Short labels in formalize.LLM_MAP map to OpenRouter model ids (pro → openrouter/google/gemini-3.1-pro-preview, flash → openrouter/google/gemini-3-flash-preview, ...). Override any of them via env vars (MSA_LLM_PRO=...) or pass a full model id directly.

Stage 3 — top-level driver

python msa.py --scenario {id} --expt {1|2}
             [--llm flash] [--n-runs 3] [--k-graph 4]
             [--max-parallel 4] [--force]

python msa.py --sport {biathalon|canoe-race|tug-of-war} --expt {1|2}
             # same flags; expands to all T=7 ids from data/test_ids.json

For each (scenario, run) the driver:

  1. Loads the test scenario (data/test-scenarios/e{e}/scenarios/{id}.txt).
  2. Calls formalize() to produce the WebPPL model and the step-1 parse block.
  3. Prepends var queryLabels = {...} built from the scenario's Query N: ... lines (the LLM doesn't produce labels).
  4. Saves models/msa_{llm}_e{e}_r{r}/{id}.wppl and runs get_samples.js to produce samples/msa_{llm}_e{e}_r{r}/{id}.json (1000 samples).
  5. Builds a gold-for-this-test-scenario model: takes models/gold/{sport}.wppl, strips its hard-coded // CONDITIONS/return block, and splices in the LLM-parsed conditions + a new return block synthesised from the parsed query expressions. Saves to models/gold_e{e}/{id}.wppl and runs inference into samples/gold_e{e}/{id}.json.

Concurrency: --n-runs MSA runs for one scenario run concurrently (each internally fans out K graph workers); --max-parallel scenarios in flight at once for --sport mode. Each MSA run has its own RNG seed so example-shuffling differs across runs.

Caching (on by default)

For each run, if samples/{method}_r{r}/{id}.json and the cached parse block (intermediates/.../1_parse_block.txt) both exist, the driver skips the LLM and inference entirely and re-reads the parse block from disk. Gold has its own check on samples/gold_e{e}/{id}.json. The status line shows what was cached vs recomputed, e.g.

✓ tug-of-war_effort_team-...: ok (2 MSA fresh, 1 MSA cached, gold fresh)

Pass --force to ignore the cache and recompute from scratch.

Outputs

samples/msa_{llm}_e{e}_r{r}/{id}.json     # one per run
samples/gold_e{e}/{id}.json               # one per scenario
models/...                                 # parallel structure
intermediates/{method}/{id}/{1_parse_*, 2_graph_*, 3_model_*}

Stage 4 — comparison + figures

plot_vs_gold.py

python plot_vs_gold.py --sport {sport} --method {base_method} --expt {e}
python plot_vs_gold.py --scenario {id}  --method {base_method} --expt {e}

For each test scenario in the sport, computes per-query MSA mean (across N runs) and gold mean. Probability queries (range [0, 1]) are auto-scaled to 0–100 so all queries share a 0–100 axis. Writes two figures to comparisons/{method}_vs_gold_e{e}/:

  • {sport}_per_scenario.png — 2×4 grid, one subplot per test scenario (the 8th panel is empty when T=7), each showing the 8 queries as points with error bars (MSA std across runs on x, gold SEM on y). R² annotated.
  • {sport}_by_query_type.png — 3 panels for the query-type stratification used in Fig 6 of the paper: constant (q1–3, intrinsic rank), temporal (q4–6, in-match effort/accuracy), prediction (q7–8, new-match outcomes). Each panel pools the T scenarios for that group, color-coded by scenario.

compare_samples.py

Single-pair distributional comparison (python compare_samples.py --method1 ... --method2 ... --model X). For each query: 2×1 panel histogram, KS p-value, permutation-test p-value on Wasserstein, JS distance. Writes comparisons/{m1}_vs_{m2}/{model}/comparison.html with the per-query metrics table at the top. The JS-distance noise floor at N=1000, K=30 bins is ~0.10 (see docs/jsd.tex for the derivation).

Smoke test

test/msa_smoke.py runs the full pipeline on the first tug-of-war E1 test scenario with --llm flash --n-runs 1 --k-graph 1 --expt 1. About 3 LLM calls + 2 WebPPL inferences, ~30s end-to-end. Use this whenever you change prompts, pipeline plumbing, or the comparison code. Subsequent runs return in <1s thanks to the cache; pass --force to revalidate from scratch.

Recommended P-vs-Q test

JS distance has a non-trivial noise floor at our settings. For deciding whether two methods produce samples from the same posterior:

  • Per-query: two-sample Kolmogorov–Smirnov (scipy.stats.ks_2samp) on raw samples — no binning, calibrated p-value.
  • Effect size: Wasserstein distance plus a permutation test for its p-value.
  • Family-level: histogram of per-query p-values across queries (uniform on [0, 1] under H0).
  • Yardstick: gold-vs-gold1 gives a noise-floor baseline — e.g. ~0.10 JSD for N=1000, K=30 bins.
